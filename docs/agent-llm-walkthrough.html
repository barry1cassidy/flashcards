How Zipdeck’s agent talks to an LLM

A walkthrough of Create With AI and Edit Cards with AI: how the UI starts a job, how Spring AI sends prompts + tool definitions to Gemini (OpenAI-compatible API), and how the model drives real side effects by calling tools.

Open these while you talk
  1. backend/.../agent/AgentController.java — HTTP entry
  2. backend/.../agent/AgentService.java — prompt + ChatClient + job runner
  3. backend/.../agent/AgentTools.java — create tools (createSet / createDeck / addCards)
  4. backend/.../agent/AgentEditTools.java — edit tool (proposeChanges)
  5. frontend/src/pages/AgentPage.jsx — Create With AI UI + poll
  6. frontend/src/pages/EditCardsWithAi.jsx — Edit with AI UI + poll

1. Big idea

The model never writes SQL or touches React state directly. We give it a system prompt, a user message, and a list of tools (Java methods annotated with @Tool). When the model wants something done, it returns a tool call. Spring AI runs that Java method, sends the JSON result back to the model, and repeats until the model returns a normal text reply (or we finish the job from tool side effects).
Browser
User describes a deck or an edit. UI POSTs and polls a job.
↓
API
AgentService builds ChatClient prompt + registers tool object.
↓
LLM
Gemini (via OpenAI-compatible base URL). Returns text and/or tool_calls.
↓
Tools
Java methods create decks/cards or collect edit proposals. Results feed back into the model.

Create tools the model can call

Declared with Spring AI @Tool / @ToolParam. Descriptions become the schema the model sees.

ToolLinesSide effect
listSets AgentTools.java:127–140 Read-only list of the user’s sets
createSet AgentTools.java:142–173 Optional folder for the new deck
createDeck AgentTools.java:175–229 Creates the deck row (once per request)
addCards AgentTools.java:231–283 Bulk-inserts card fronts/backs/hints; enforces max card limit 
// AgentTools.java — what the model “sees” as a function
@Tool(description = """
        Create exactly one flashcard deck for this request.
        Put it in preferredSetId or a set you just created when that makes sense.
        """)
public String createDeck(
        @ToolParam(description = "Deck name") String name,
        ...
) { ... return "{\"deckId\":\"...\",\"name\":\"...\"}"; }
Typical create sequence the model chooses: createDeck → addCards (sometimes listSets / createSet first). Each tool return value is JSON the model reads before the next call.

4. Edit Cards with AI — same pattern, different tools

Create

Tools write to the database while the model runs.

Deck + cards exist before the job “completes.”

Edit

Tool only proposes changes. User reviews a preview, then the app applies them.

Safer for mutating an existing deck.

  1. UI — EditCardsWithAi.jsx (~194–218)
    POST /api/agent/decks/{deckId}/edits?jobId=… with the instruction; poll the same job endpoint.
  2. Snapshot cards into the user message
    AgentService.java:211–216, 627+
    Instruction + JSON array of {id, front, back, hint} so the model has exact ids.
  3. Edit system prompt forces one tool
    AgentService.java:51–63 
    You edit cards in an existing flashcard deck. You must call the proposeChanges tool.
Do not only describe the edits in text.
Change only what the instruction asks. Omit every card that should stay the same.
Use each card id exactly. Do not invent ids, add cards, or delete cards.
  4. LLM call
    AgentService.java:565–570 
    chatClient.prompt()
        .system(EDIT_SYSTEM)
        .user(editUserMessage(...))
        .tools(tools)     // AgentEditTools
        .call()
        .content();
  5. proposeChanges
    AgentEditTools.java:48–119
    Validates ids, drops unchanged text, stores AgentCardChange proposals, returns a small JSON summary (accepted, unknown, …). returnDirect = true stops the model from needing another round after a good proposal.
  6. finishEdit — AgentService.java:596–611
    If there are changes, charge a credit and return an AgentEditPreview for the UI. Applying the diffs to the DB is a separate user action after review.

5. The tool-calling loop (what happens on the wire)

Spring AI’s ChatClient + OpenAiChatModel speak the OpenAI tools protocol to Gemini’s OpenAI-compatible endpoint (AgentProperties.java:21–24, AgentService.java:428–440).

One agent turn (simplified)
API → LLM
Messages: system + user (+ prior tool results).
Also: tool schemas derived from @Tool methods (name, description, JSON parameter schema).
↓ model decides
LLM → API
Either a final assistant text message,
or one or more tool_calls like { name: "addCards", arguments: { deckId, cards: [...] } }
↓ if tool_calls
API runs Java
Invokes the matching method on AgentTools / AgentEditTools. Progress step recorded on the job (UI can show “Adding cards…”).
↓ tool result message appended
API → LLM
Send tool output JSON back. Model may call another tool or finish.
We set parallelToolCalls(false) (AgentService.java:438) so the model creates the deck before dumping cards in parallel. Tool call caps: create ≤ 12 (AgentTools.java:27), edit ≤ 6 (AgentEditTools.java:14).

Progress the user sees

Each tool call does progress.step(code, detail) (AgentTools.java:285–291). The UI polls the job and maps those codes to friendly copy (“Calling the model…”, “Creating deck…”, “Adding cards…”).

6. Suggested talking order (≈10 minutes)

  1. Open Create With AI in the app. Explain: the browser only starts a job and polls; the model never talks to the browser.
  2. Jump to AgentController → startCreateDeck → show the async handoff.
  3. Show chatClient.prompt().system().user().tools(tools).call() — this is the whole interface.
  4. Open AgentTools and walk one @Tool method: description → args → JSON return.
  5. Sketch the loop on a whiteboard: model asks for createDeck, gets deckId, then calls addCards.
  6. Contrast with AgentEditTools.proposeChanges: same loop, but no immediate DB write — preview + human confirm.
  7. Optional: mention provider wiring — Gemini over OpenAI-compatible URL, not a custom Gemini SDK (AgentProperties / openAiChatModel()).
What this is not: a live chatbot or streaming token UI. It is a job-shaped agent: one user goal, tools with side effects (or a preview), then a finished job record. Language Studio generation is a separate feature path; this walkthrough is specifically Create / Edit deck with the agent.
